# Mobile loading and playback verification — 2026-10-01

Local production build after PR53. The synthesis library now loads when
playback is requested. A native AudioContext is created/resumed synchronously
inside the user gesture before the dynamic import; graph playback uses the
same unlock path before its realization request.

## Passed

- Frontend lint, typecheck, all 31 unit tests, and production build.
- Two generator Chromium scenarios, including actual `Playing` transport
  state and parseable MIDI export, plus two graph scenarios.
- Three clean mobile Lighthouse runs: performance **90, 91, 91**;
  accessibility **100, 100, 100**. All reports have no runtime error.
  The same-session pre-change baseline was 68/100 with 967 ms total blocking
  time; the first post-change run had 174 ms. The corpus build was running
  during these measurements, so absolute timings include local contention.
- This closes the repeatable local mobile >=80 performance and >=90
  accessibility measurement. It does not establish production L03 acceptance.

Lighthouse JSON reports are `.agent-logs/lighthouse-after-lazy-{1,2,3}.json`.
As in the earlier Windows runs, the CLI exited 1 during temporary Chrome
profile cleanup (`EPERM`), after completing valid reports. That cleanup
failure is recorded separately from the audited page results.

## WebKit runner limitation

The Windows Playwright WebKit runner passed the comparison scenario but
failed the playback assertion because neither `AudioContext` nor
`webkitAudioContext` is available in that runner. The UI displayed the
explicit unsupported-browser error. This does not verify Safari/iOS playback
and is not counted as a playback pass.

## Still unverified

Human listening and Safari/iOS device behavior; actual production corpus UI,
