# ADR-003 — Function tokens are mode-aware and two-level

**Status:** Accepted (roadmap v2)

**Context:** Roman-numeral analysis needs both a compact,
poolable graph vertex (so `V7/vi` in one song and another are the
"same" node for statistics) and a full display form that keeps
inversions, extensions, and applied targets legible to a
musician. A single flat string can't do both without either
exploding the vocabulary or losing information.

**Decision:** Every chord gets a `core` token used as the graph
vertex — `MODE:ACC*NUMERAL QUAL? ("/" TARGET)?`, e.g. `M:V7/vi`,
`m:VII`, where `M`/`m` is the local mode — and a separate `figure`
carrying the full display form including inversions and
extensions, e.g. `V65/V`, `IVmaj9`, `viiø7`. The absolute
(spelled) chord identity is always preserved alongside both. The
full grammar is defined once in the implementation plan §2 and
reused everywhere (analysis, graph, prediction, color).

**Consequences:** Graph and n-gram statistics pool correctly
across extensions/inversions of "the same" function; every
schema and API response must carry three related-but-distinct
fields (`core`, `figure`, `chord`) instead of one; the grammar
must be implemented once and imported everywhere rather than
re-derived per feature.

**Revisit trigger:** If a downstream consumer needs a different
level of granularity than `core` provides (e.g., pooling `V7` and
`V` together), reconsider the token grammar rather than adding a
fourth ad hoc representation.
