# ADR-009 — Next.js security upgrade; vitest CVE deferred

**Status:** Accepted (2026-09-23)

**Context:** `npm audit` on the harmonic-color-graph frontend
reported 16 vulnerabilities (2 low, 5 moderate, 8 high, 1
critical). The most severe were a critical RCE bundle in `next`
itself and a high-severity `sharp` (image optimization) chain,
both pulled in directly by the pinned `next@16.2.7`. A second,
unrelated cluster (`qs`, `hono`, `express`, `ip-address`,
`js-yaml`, `fast-uri`, `body-parser`, etc.) turned out to come
from `shadcn`'s bundled MCP server/CLI tooling
(`@modelcontextprotocol/sdk` → `express` →
`body-parser`/`qs`), not from Next.js — worth recording since the
two are easy to conflate from the audit output alone. Registry
metadata showed the `next` 16.2.x patch line stopped receiving
releases after `16.2.12` (2026-07-25); only the `16.3.x` line is
still active (`16.3.6`, released 2026-09-22).

**Decision:** Ran `npm audit fix` (no `--force`) first, which
resolved the entire `shadcn`-originated cluster (11 of 16
findings, including `qs`) via `package-lock.json` only — no
`package.json` or code change. For the remaining `next`/`postcss`/
`sharp` bundle, reviewed the actual GitHub release notes for
every stable tag between `16.2.7` and `16.3.6` rather than
relying on training data (this environment's clock is
2026-09-23, past this model's knowledge cutoff, and the registry
is the real npm registry). `16.3.0` carries real behavioral
changes (cache components/app shells enabled by default, Edge
Runtime deprecated, legacy PPR codepaths and a few experimental
flags removed), but this app has an empty `next.config.ts`, no
middleware, no Server Actions, no edge runtime, and no
`next/image`/`next/og` usage — none of that surface applies here
today. `16.3.3` fixes the two critical Windows/AVIF RCEs listed
in the original audit; `16.3.6` additionally fixes a critical
`next/og` RCE (GHSA-vcvr-r3jv-pc5j) that isn't yet listed in
npm's advisory data. Bumped `next` and `eslint-config-next` to
`16.3.6` (keeping the project's existing exact-pin convention)
and reinstalled. `scripts/check.ps1 all` (backend ruff/pytest +
frontend lint/typecheck/vitest/build) passed clean both before
and after, and was re-verified against a pre-upgrade baseline run
on `16.2.7`.

Left one moderate finding unresolved: `@vitest/mocker` (path
traversal / arbitrary file read via redirect mock — dev-only, it
runs under `vitest` and is never shipped to production).
`npm audit fix --force` wants to jump straight to
`vitest@5.0.1`, which requires Node `^22.12 || ^24 || >=26` —
incompatible with this repo's `.nvmrc` (Node 20). A smaller,
Node-20-compatible fix exists (`vitest@4.1.11`, which already
bundles a patched `@vitest/mocker`), but 3→4 is its own breaking
migration that deserves dedicated review and test-suite
verification, not a drive-by bump alongside a Next.js CVE fix.

**Consequences:** Frontend is now clean of every Next.js/image
-pipeline advisory ahead of the v2 plan's F06/F07 (Vercel deploy)
and F85 (v1.0 release) gates. One moderate, dev-only advisory
remains open (`@vitest/mocker`) — no production exposure today
since the app isn't deployed yet, but it should be closed before
F85. `eslint-config-next` must keep tracking `next`'s exact
version on future bumps (matching the pin style already used for
both).

**Revisit trigger:** Before F85 (v1.0 release) — migrate `vitest`
3.2.7 → at least `4.1.11` (review the 3→4 changelog first; do not
jump to `vitest@5.x` without also moving `.nvmrc`/CI off Node
20). Also re-run `npm audit` again right before F06/F07 deploy,
since `next` 16.3.x is still receiving frequent patches.
