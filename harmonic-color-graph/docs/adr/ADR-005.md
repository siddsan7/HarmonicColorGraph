# ADR-005 — Single migration system

**Status:** Accepted (roadmap v2)

**Context:** Phase 1 had two migration systems in parallel:
SQLAlchemy/Alembic locally and ad hoc schema application through
the Supabase MCP tools directly against the remote project. They
drifted (some tables were created by one path but never written
by the other), and CI cannot practically run Alembic against a
disposable Postgres container the same way it can apply plain
SQL.

**Decision:** SQL files under `supabase/migrations/` are the
single source of truth, applied through the Supabase MCP
`apply_migration` tool (or CLI) against the real project and
through `psql` against a `pgvector/pgvector:pg17` container in
CI. Alembic is retired: `backend/alembic/` and `alembic.ini` move
to `backend/legacy/alembic/` with a README noting the history,
and Alembic is dropped from dependencies. `list_migrations` must
always equal the files in `supabase/migrations/`.

**Consequences:** One migration history to reason about; schema
changes are plain, reviewable SQL; local Postgres setup (for
`seed_corpus --create-schema`-style flows) must execute the same
SQL files rather than an Alembic `upgrade head`.

**Revisit trigger:** If the team ever needs Alembic's
autogeneration or Python-side data migrations badly enough to
justify re-introducing a second system — not expected pre-launch.
