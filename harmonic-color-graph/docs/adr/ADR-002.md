# ADR-002 — Postgres property graph instead of Neo4j

**Status:** Accepted (roadmap v2)

**Context:** The derived harmonic graph is small — on the order
of 10k nodes and hundreds of thousands of edges. A dedicated
graph database adds a third managed service on top of Supabase
and Vercel, with its own free-tier pausing behavior, for a graph
that fits comfortably in relational tables.

**Decision:** Store the graph as typed Postgres tables in
Supabase: `hcg.nodes(id, type, label, props)` and
`hcg.edges(src, dst, type, context_id, count, prob, weight,
props)` with per-type partial indexes. Multi-hop queries stay
≤ 2-hop SQL; k-shortest-path and constrained search run in
Python over a small in-memory cached subgraph (a few MB per
context). Embeddings live in pgvector, in the same database.
The pipeline writes a neutral node/edge artifact, so an optional
Neo4j/AuraDB export (S1) stays possible without changing the
source of truth.

**Consequences:** One fewer managed service and failure mode;
graph algorithms (paths, FastRP, communities) are hand-written in
Python/NumPy instead of using a graph engine's built-ins; no
ad-hoc Cypher exploration for non-developers unless S1 is built.

**Revisit trigger:** The edge count approaches ~5M, or a feature
needs ad-hoc Cypher-style exploration by non-developers.
