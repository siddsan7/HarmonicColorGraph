Where the repo is solid, and where it will bite next

A static read of every tracked source file across the FastAPI service, the offline corpus pipeline, SQL migrations, the Next.js workbench, and CI. Each finding cites the file that proves it, says why it matters for this project specifically, and names the fix.

commit 994b648 branch docs/migration-0007-applied audited 2026-09-24 milestone M4 · next is F41 active corpus cv-2026-09-a

The architecture is in good shape. Stores own SQL and services own the logic. Every read is scoped by corpus version. Loads are all-or-nothing, with a storage gate. Jobs are durable and idempotent. Prediction quality sits behind a leak-free evaluation gate. Nothing found here needs a redesign.

The risk is at the edges: the backend's dependency versions aren't pinned, production rate limiting probably doesn't work, and agents are still being pointed at context docs that contradict the code. That last one matters more here than in most repos, because agents do most of the building.

Findings

Ranked by severity, then by how soon each will cost something. Most severe first.

A-01

Backend dependencies are unpinned, and Vercel resolves them fresh on every deploy

Highsupply chain
Evidence
backend/pyproject.toml declares floors only (fastapi>=0.124, pydantic>=2.12, sqlalchemy>=2.0.45, psycopg[binary]>=3.2). Only redis<7 is capped. The repo has no uv.lock, requirements.txt, or constraints file. The frontend, by contrast, pins exact next/react and ships a lockfile.
Why it matters
A production deploy can pick up a new FastAPI, Starlette, or Pydantic release that CI never ran against. CI also resolves its own latest set on each run, so a green PR doesn't prove what production installs. The API runs on its own Vercel project with no human watching builds.
Fix
Generate a lock (uv pip compile pyproject.toml -o requirements.txt, plus --extra dev,pipeline for CI). Have Vercel and CI install from it, and add --upgrade refreshes as deliberate PRs.
A-02

Public rate limits are probably not limiting anyone in production

Highsecurityverify
Evidence
  • The subject is request.client.host (app/api/graph_v2.py:37, app/api/recommend_v2.py:44). Browser traffic arrives through the Next.js rewrite (next.config.ts), so the API may see a proxy address shared by every user, or a different one per edge node. Neither is the real client.
  • Every limit is fail_mode="open", and RateLimiter.check returns allowed when REDIS_URL is unset (app/core/cache.py:190-197). Whether production Vercel has REDIS_URL set is undocumented.
  • /v2/analyze, /v2/graph/explain-edge, /v2/graph/node, and /v2/examples have no limit at all.
Why it matters
The Supabase free tier is the scarcest resource (500 MB, a 5 s statement timeout, pausing). One client looping /v2/graph/path could saturate it. If every user shares one key, the opposite failure applies: 30 path requests per minute locks out everyone at once.
Fix
Log client.host and x-forwarded-for from one preview deployment to learn the real shape. Key limits on the trusted forwarded address, confirm Redis in production, and add a coarse limit to the unlimited routes.
A-03

The docs agents read first contradict the code

Highagent context
Evidence
  • context/progress-tracker.md "In Progress", "Next Up", and "Session Notes" still say F10 is uncommitted, that phase-one-demo.tsx is the app shell, and that no backend exists.
  • context/code-standards.md says "Use Alembic for schema migrations", against ADR-005.
  • context/architecture.md puts the proxy in a vercel.json rewrite (it lives in next.config.ts), labels built directories "Planned", and describes a public/snapshot/graph-core.json fallback that doesn't exist.
  • ADR-009 says next.config.ts is empty.
  • Stale code comments in pipeline/cli.py:18, app/predict/ngram.py:31, app/core/redis.py:1, pipeline/stages/_context.py:7, and the ci.yml backend-pg env comment.
Why it matters
AGENTS.md tells every agent to read these files before acting, and the user has authorized agents to merge their own PRs. A stale instruction becomes a merged mistake, and the Alembic line is exactly the kind of instruction an agent follows literally.
Fix
Delete the three stale progress-tracker sections (their history is in the Completed log). Change the Alembic line to point at supabase/migrations/. Correct the architecture proxy and boundary text and mark the snapshot as F63. Refresh the five comments. Until then, context/brain/gotchas.json → docs-stale-sections warns agents off.
A-04

No automated dependency vulnerability scanning

Mediumsecurity
Evidence
.github/ has only workflows/ci.yml: no Dependabot config, no npm audit step, no pip-audit. The critical Next.js RCE that ADR-009 fixed was found by a manual npm audit. The fix itself sat in an abandoned worktree until it was recovered as PR #14.
Why it matters
Both services are public and deploy automatically from main. The last critical advisory was caught by luck.
Fix
Add .github/dependabot.yml for npm, pip, and github-actions. Add CI steps npm audit --omit=dev --audit-level=high and pip-audit against the lock from A-01.
A-05

Graph neighborhood makes one query per edge

Mediumperformance
Evidence
app/graph/service.py:98-110: for every candidate edge, self.store.node(edge["dst"]) is a separate SQL round trip through the Supabase transaction pooler. With limit=200, hops=2 that is up to ~400 sequential queries per cache miss. Each query also runs through the edges_read view's three joins.
Why it matters
Serverless functions pay pooler latency on every trip. A high-degree node like function:M:I in the global context is exactly what the F63 Graph Explorer will request first, uncached, after each corpus flip.
Fix
Add GraphStore.nodes(ids) (where version = hcg.v() and id = any(:ids)) and fetch each hop's destinations in one batch. paths() has the same per-node pattern, softened by its local node_cache.
A-06

Hand-written frontend types bypass the generated contract

Mediumcontracts
Evidence
lib/api/client.ts:16-172 declares its own Recommendation, RecommendResponse, SongExample, ExamplesResponse, NextChordsResponse, and more. Only AnalysisV2/AnalyzeV2Request come from the generated lib/api/types.ts.
Why it matters
CI's drift gates (export_openapi.py and gen:api) only prove the generated file is fresh. A backend field rename passes CI and fails at runtime in the recommendations panel. M4–M6 will add color, generation, and graph payloads through this same client.
Fix
Alias every client type from components["schemas"]. Keep only the runtime guards hand-written.
A-07

Mediumrelease
Evidence

Why it matters

A-08

Repeated version and context round trips on every request

Lowperformance
Evidence
One recommendation runs select hcg.v() separately in RecommendationService.recommend, KNPredictor._discounts, and SessionNgramReader.count_of_counts. It also runs up to four context_by_key queries. Graph routes call active_version() for the cache key and again in _response(). KNPredictor._discount_cache is rebuilt per request (RecommendationService.from_session), so it never hits; _COUNT_CACHE is what actually works.
Fix
Resolve the version once per request and pass it down. Cache the contexts table per version (it holds only ~3k rows and its IDs are stable). Delete the per-instance discount cache or make it module-level.
A-09

Lowapi consistency
Evidence

What's already done right

Keep these patterns. New work should copy them rather than invent alternatives.

Store owns SQL, service owns logic

GraphStore/GraphService and NgramStore/KNPredictor. Migration 0006 swapped the count-of-counts SQL without touching the predictor.

Version-scoped everything

Every read filters version = hcg.v(), and every cache key includes the version. A corpus flip takes effect on the next statement.

All-or-nothing loads

COPY, validation, storage gate, ANALYZE, and activation run in one transaction. A failed load leaves the previous corpus serving, which the two aborted M2 loads proved.

Durable jobs, disposable queue

Postgres is the ledger and Redis only wakes workers. Leases, reconciliation, idempotency keys, and dead letters are in place, job types are allowlisted and typed, and artifact paths are guarded against traversal.

Serverless-safe database access

NullPool, no prepared statements, a lazy session factory, a 5 s statement timeout, and an hcg-first search path.

Evidence-gated quality

A leak-free evaluation is a hard gate, and the MRR win over v1 is measured, not asserted. Contract drift checks and a real queued job in the Compose smoke run on every PR.

Blast-radius guards

memory_guard kills runaway stages. Redis outages bypass caches, and analysis keeps working with the database down.

Method and limits

  • Static read of git ls-files at 994b648: every backend module, every migration, the frontend, CI, and the configs. Line references are to that commit.
  • No production calls were made. Findings tagged verify depend on deployment configuration this audit could not see.
  • Documentation was cross-checked against code, and each finding cites the side that wins. Anything already recorded in context/HANDOFF.md is referenced, not restated.
  • Companion files: docs/codemap.html (structure) and context/brain/gotchas.json / facts.json (agent rules and code-verified values).
