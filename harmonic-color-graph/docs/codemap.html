Runtime topology

Two Vercel projects deploy from one repo. The browser only ever talks to the web origin. FastAPI is the only process that reads the hcg schema at request time. Corpus data enters the database solely through the versioned loader.

Request flows

The steps each operation runs, in order. ↯ SQL marks a database round trip, which matters under the 5 s serverless statement timeout and pooler latency.

Analyze → recommend

Analyze button in WorkbenchV2

  1. analyzeProgressionV2 → POST /v2/analyze. analyze_v2 normalizes chords, estimates song and section keys (24-key softmax), romanizes functionally, and applies relationships_v2 rules. No database.
  2. The UI renders tokens and keys, then fires recommendNextChords with the .core tokens, song_key, and genre/section (abortable).
  3. RateLimiter.check runs a Redis EVAL fixed window; it allows the request if Redis is down.
  4. select hcg.v() ↯ SQL returns 503 corpus_unavailable if no version is active.
  5. _input_tokens validates core tokens against the key's mode, or re-runs analyze_v2 on raw chords.
  6. _resolve_chain runs one context_by_key query per level: genre_section → genre → section → global ↯ ×≤4. Missing contexts drop out of the chain.
  7. NgramStore.histories fetches every (context, order, history) in one query ↯ SQL.
  8. Discounts come from ngram_discount_stats ↯ SQL on cache miss (_COUNT_CACHE, keyed by version).
  9. Interpolated KN runs within each context and is mixed across contexts (β = n/(n+K), K = 100). The top 100 are filtered to the history's mode and realized to chord symbols, stopping at limit.
  10. transition_examples_many (≤2 each) ↯ SQL and FactStore.existing_ids ↯ SQL.

Output: recommendations with score_breakdown, evidence, fact_ids, and a templated explanation, plus context_backoff / key_ambiguous warnings. Clicking a chord appends it and re-runs from step 1. In parallel, EvidencePanel calls /v2/examples once per distinct transition.

Graph neighborhood / path

GET /v2/graph/neighborhood · POST /v2/graph/path

  1. The public guard applies the rate limit (120 or 30 per 60 s).
  2. active_version() ↯ SQL builds the cache key hcg:<version>:graph:*:<hash>. It checks L1 (per process, 256 entries), then L2 Redis.
  3. Miss, neighborhood: context_by_key ↯ and the root node ↯. Per hop, outgoing_edges ↯, then one node() per kept edge ↯ ×N.
  4. Miss, path: the whole function_adjacency for the context ↯ once per version goes into _ADJACENCY_CACHE, then a best-first search with cost −ln p (+0.5 for non-transition edges) and an optional chromaticity constraint.
  5. The result is written to L1 and L2 (TTL 1 h). _response() re-reads the active version ↯ SQL for meta.

Node IDs accept the M:I shorthand (prefixed function:). Unknown context → 422; missing node → 404.

Durable job

POST /v2/jobs with token + Idempotency-Key

  1. A typed, allowlisted request: graph_rebuild | evaluation_run (embedding_rebuild returns 409).
  2. JobRepository.create ↯ SQL writes the jobs row plus idempotency_keys. A replay returns the same job; a different payload under the same key returns 409.
  3. JobQueue.enqueue: SET NX hcg:jobs:queued:<id> EX 60 + LPUSH hcg:jobs:ready. If Redis is down, the API returns 503 and the row stays queued.
  4. The worker BRPOPs the ID, claims it with a 90 s lease ↯, and a heartbeat thread renews it every 30 s.
  5. run_job → handler: pipeline.load.load_corpus, or evaluate_keys|labels_corpus. Progress goes to job_events.
  6. The job ends complete, or fail → retrying (with available_at) or dead_letter once attempts ≥ 3.
  7. Every 30 s: recover_expired leases and re-enqueue all queued IDs.

Delivery is at-least-once. Handlers must be idempotent, and Postgres is the truth.

Corpus build → activate

hcg-build run --version cv-… then load

  1. Stages run under MemoryGuard and write Parquet plus manifest.json (hashes, row counts, budget estimate).
  2. load_corpus takes pg_advisory_xact_lock('hcg.corpus_loader') and sets statement_timeout = 20min.
  3. It validates required artifacts, columns, and the manifest budget estimate (≤300 MB).
  4. It inserts an inactive corpus_versions row and upserts contexts (stable IDs, 0 = global).
  5. It COPYs nodes, edges_compact (contextual edges with count < 5 dropped), n-grams, patterns, examples, song_refs, and facts. Then it populates ngram_discount_stats.
  6. It checks table counts, runs ANALYZE, and applies the size gate (hcg ≤300 MiB, DB ≤400 MiB).
  7. It flips active and commits. Any error rolls everything back, and the old version keeps serving.

garbage_collect(confirm=True) removes inactive versions. The loader's direct URL comes from gitignored backend/.env.

Database (hcg schema)

Source of truth: supabase/migrations/*.sql. 0001–0007 are applied live; 0008 is written but not yet applied (see the schema note below). Corpus tables carry a version column (edges carry version_key), and reads resolve the active one through hcg.v().

Versioning 0002 · 0005

  • corpus_versions version, manifest, active (≤1 true), version_key identity0005
  • contexts id smallint (stable; 0 = global), type, value, label
  • hcg.v() SQL function → active version text
  • active_version view

Harmonic graph 0002 · 0005 · 0007

  • nodes (version, id) PK, type, label, props; node_key identity0005
  • edges_compact version_key, src_key, dst_key, type_code 1–7, context_id, count, prob, weight (PMI), support, props0005/0007
  • edges_read view: decodes keys to text IDs and type names, and merges pmi/support into props0007
  • edges: original text-keyed table, kept empty0002

Prediction 0002 · 0006

  • ngram_histories (version, context_id, ord, history) → total, distinct_next, next jsonb, cont jsonb
  • ngram_discount_stats (version, context_id, ord) → n1, n2. Loader-maintained, so the request never scans jsonb0006

Evidence 0002

  • patterns pattern, length, support, song_count, rotations_observed, context_lifts
  • pattern_examples / transition_examples ranked song positions
  • song_refs song_id, spotify_id, genre, decade
  • facts (fact_id, version), kind, subject, template, params
  • relationship_types catalog
